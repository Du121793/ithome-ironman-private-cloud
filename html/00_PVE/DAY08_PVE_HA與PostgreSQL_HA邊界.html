Day 08｜節點故障後 VM 如何接手：Proxmox VE 遷移、HA 隔離與恢復時間量測

對應文章：Day 08｜節點故障後 VM 如何接手：Proxmox VE 遷移、HA 隔離與恢復時間量測

本日只處理 Proxmox VE 的高可用，不提前討論尚未部署的 PostgreSQL 或 Patroni。Day 07 已建立 ceph-vm RBD Storage，因此可以用可丟棄測試 VM 實際展示 Migration 與 PVE HA Recovery；但三台 Nested PVE、三個虛擬 OSD 與所有 VM 最終仍位於同一台 L0，不能宣稱已完成實體主機層的正式 HA。

1. 先盤點 PVE HA 前置條件

  1. 登入 Cluster → Datacenter → Storage。
  2. 檢查 ceph-vm 的 Nodes、Shared 與 Content，並執行 ceph -s 確認健康。
  3. 選一台測試 VM → Hardware，確認每顆磁碟是否都位於 ceph-vm。
  4. 到 Datacenter → HA，展示 Affinity Rules、Resources、Status。PVE 9 已使用 HA Affinity Rules 取代舊版 Groups，所以畫面沒有 Groups 是正常的。
  5. Shell 執行：
pvecm status
pvesm status
ceph -s
ha-manager status

如果 VM 磁碟仍只存在某一節點的 local-lvm，節點消失後其他節點讀不到該磁碟。只有已移至 ceph-vm 的可丟棄測試 VM 才進行本日 HA 實驗；僅把 local-lvm VM 加進 HA Resources 不會憑空複製磁碟。

2. 使用可丟棄 VM 建立 HA Resource

使用 Day 06 的 cloudinit-test01，或重新建立一台 VMID 902 測試 VM：

  1. 關閉測試 VM。
  2. 選 VM → Hardware → 選系統磁碟 → Disk Action → Move Storage。
  3. Target Storage 選 ceph-vm，勾選成功後刪除來源磁碟，按 Move disk。
  4. 等待 Task 顯示 OK，再確認 Hardware 中該磁碟位於 ceph-vm。
  5. 啟動 VM，確認 Guest 正常後再關機。
  6. 選 Datacenter → HA → Resources → Add。
  7. Resource 選測試 VM。PVE 9 的視窗不再提供 Group 欄位，因為舊版 HA Groups 已被 HA Rules 取代。
  8. Max Restart、Max Relocate 與 Comment 先使用預設值，再按 Add。目前的 PVE 9 新增視窗沒有 Requested State 欄位；新增既有 VM 為 HA Resource 時，預設 Request State 是 started，HA Manager 可能會立即把剛才關閉的測試 VM 啟動。
  9. 加入後查看 HA → Status，並執行：
ha-manager config
ha-manager status

ha-manager config 中的 vm:902 應顯示 state started。如果實際不是 started，才使用：

ha-manager set vm:902 --state started

只有測試 VM 的全部磁碟都能被目標節點取得時，才進一步測試 Migration／Recovery。Cloud-Init Disk 也必須位於 ceph-vm，不能只搬系統磁碟。

3. 建立 HA Node Affinity Rule

PVE 9 將舊版 HA Group 的節點偏好功能改成 Node Affinity Rule。Rule 會引用已存在的 HA Resource，因此先完成上一節，再建立 Rule。

  1. 選 Datacenter → HA → Affinity Rules。
  2. 在 HA Node Affinity Rules 按 Add。
  3. Resources 選剛加入的測試 VM，例如 vm:902。
  4. Nodes 加入 pve01、pve02、pve03。
  5. Strict 不勾選。非 Strict Rule 表示優先使用列出的節點，但這些節點都不可用時仍可選擇其他可用節點；Strict Rule 會把資源限制在指定節點，全部不可用時資源會停止。
  6. Comment 填 Day08 lab node affinity，其他欄位使用預設值後按 Create。

本 Lab 只有三個節點，將三台全部列入 Rule 主要是展示 PVE 9 的設定位置與資料結構。正式環境才依硬體能力、Storage 可達性與故障域設定節點清單及 Priority。

同一頁另有 HA Resource Affinity Rules，用來要求多個 HA Resource 盡量一起運作或彼此分散。本日只有一台測試 VM，因此不在該區塊新增 Rule。

4. 先確認 CPU Type 是否適合 Migration

在測試 VM 的 Hardware → Processors 查看 CPU Type，也可以執行：

qm config 902 | grep '^cpu:'

CPU type=host 不是完全不能 Migration。它會把來源 PVE Host 較完整的 CPU 指令集提供給 Guest，因此判斷重點是目標節點能不能提供相同的 CPU 能力：

  • 來源與目標是相同或高度相容的 CPU，host 通常仍能 Live Migration。
  • 目標節點缺少來源 VM 已使用的 CPU Flag，Live Migration 可能被拒絕或失敗。
  • Offline Migration 與 HA Recovery 不需要搬移正在執行的 CPU State，限制較少；但 Guest 或以來源專用指令集編譯的程式仍可能無法在較舊 CPU 上正常執行。
  • Intel／AMD 混用，或不同世代 CPU 混用時，不應把 host 當成整個 Cluster 的通用 CPU Model。

本 Lab 的 pve01～pve03 都在同一台 L0 上，看到的是同一顆實體 CPU，因此先保留 host 做 Live Migration 實驗即可。成功只證明這三台同源 Nested 節點相容，不代表不同實體硬體一定相容。

正式環境若節點硬體不同，應先盤點所有節點共同支援的 CPU 能力，再選擇共同可用的 CPU Model，例如經測試的 x86-64-v2-AES 或自訂 Cluster CPU Model。若需要修改，先關閉 VM，再到 VM → Hardware → Processors → Edit → Type；不要在本 Lab 還能正常 Migration 時為了教學強制更換。

5. 手動 Migration 與 HA Recovery 的差異

手動 Migration 是管理者主動選擇目標節點並等待搬移完成，適合維護前操作。HA Recovery 是節點被判定不可用後，由 HA Manager 依 Quorum、Watchdog／Fencing、Affinity Rules 與資源狀態決定是否在其他節點重新啟動 VM。

錄影時依序展示：

  1. 右鍵測試 VM → Migrate。
  2. 查看 Target Node 與 Storage 選項。
  3. 確認磁碟位於 ceph-vm 後執行 Live Migration，記錄完成時間與 Guest 中斷時間。
  4. 回 HA Status 確認 Resource 所在節點已更新。
  5. 再關閉測試 VM，執行一次 Offline Migration，對照兩種操作的畫面與時間。
  6. 要做 Recovery 實驗時，從 L0 關閉承載測試 VM 的 Nested PVE；觀察 HA 是否在另一節點啟動 VM，再恢復原節點。
  7. 同時記錄 ceph -s，因為停止一個 Nested PVE 也會讓一個 OSD 與 MON 離線。

6. 本 Lab 可以與不能證明的內容

可以實作：

  • HA Node Affinity Rule、HA Resource 與 HA Manager 狀態查看。
  • Quorum 對 HA 決策的影響。
  • 使用 Ceph RBD 的 Live／Offline Migration 與測試 VM Recovery。
  • CPU type=host 在三台同源 Nested 節點間的相容性結果。

不能直接宣稱：

  • 單一實體主機斷電後 VM 仍會服務。
  • 三個虛擬 Ceph OSD 等於三個獨立實體故障域。
  • 沒有可靠 Watchdog／Fencing 也能安全自動接管。
  • 這次 host Migration 成功，代表任意 Intel、AMD 或不同世代 CPU 都能遷移。
  • VM 在另一節點重新開機等於服務完全沒有中斷。

7. 正式環境補充

正式 PVE HA 至少要重新評估：三台獨立實體主機、獨立故障域、可靠 Corosync 網路、Watchdog／Fencing、共享或分散式儲存、相容的 Cluster CPU Model、UPS、備份與實際關機演練。
